Continuous Migration

Five steps, repeated until D-day

1. Target architecture

Set up your target PostgreSQL environment first — not as an afterthought once the migration is already underway.

2. Fork the CI

Fork a Continuous Integration environment that runs against PostgreSQL, alongside the one running against your current RDBMS.

3. Migrate nightly

Migrate the data over and over, every night, from current production — this is the step pgloader automates.

4. Schedule D-day

As soon as the CI is consistently green against PostgreSQL, schedule the cutover.

5. Migrate, no surprises

By D-day the migration has already run successfully many times — the cutover itself is the boring part.

Breaking the effort into these five repeatable steps is what makes a migration project pausable and resumable instead of a single high-stakes event — see the Continuous Migration page for why that matters.
